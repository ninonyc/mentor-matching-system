# Phase 4 — SQLite database design

## Install and scope

Copy this update into the existing project root, keeping paths. Files under
`database/` and Phase 4 documentation are new. No CMake or matching-core changes
are required. Your current logs/screenshots are not overwritten.

The SQL migration is the application schema. Python scripts are standalone
schema/demo test utilities using the standard-library `sqlite3` module.
The application backend remains C++; this phase does not connect the database
to the C++ matcher, implement login, expose an API, or modify the UI.

## Run

From the project root:

```bash
python3 database/demo.py
python3 database/tests/test_schema.py
```

The demo uses a fresh in-memory database by default and leaves no database
file behind. Expected output:

```text
SQLite schema version: 1
Users: 6
Participants: 5
Run state: verified
Assignments: 2
Inputs current: True
Foreign-key check: OK
DATABASE DEMO PASSED
```

The test script should end with `Ran 31 tests` and `OK`; elapsed time varies.

To create a NEW persistent demo database containing only fictional fixture data:

```bash
mkdir -p build
python3 database/demo.py --database build/mentoring-demo.db
```

This command refuses to overwrite an existing file. Use another filename for
a later demo. Do not delete a real database to make a demo command succeed.
The script seeds a known stable example by inspection; it does not execute
the C++ verifier. Actual matcher-to-database integration remains later work.

## Tables

| Table | Responsibility |
| --- | --- |
| `users` | Stable identity, display name, unique case-insensitive email, active/admin flags. |
| `matching_rounds` | Roster/preference lifecycle for one cohort. |
| `participants` | A user's mentor/mentee role in one round. |
| `preference_versions` | Owner, revision number, change explanation, draft/submitted state. |
| `preference_entries` | Ordered targets; unique target and unique positive rank per version. |
| `matching_runs` | One administrator-requested computation and its final historical state. |
| `run_preferences` | Exact submitted version used for each participant in a run. |
| `assignments` | Unique mentor and mentee per run. |
| `verification_results` | Stored C++ status, explanation, and optional blocking pair. |
| `ratings` | One rating from each assigned partner; provisional 1–5 scale. |

`run_freshness` is a VIEW, not another stored table. It checks whether a run
has all participants' inputs and no newer submitted revisions exist.
The view does not calculate stability.

## Lifecycle decisions for this first implementation

1. A round starts `collecting`. Add/remove participants before rankings start.
2. Freeze its roster: transition to `frozen`. Require m >= n.
3. In a frozen round, create preference drafts and submit complete rankings.
4. Build a matching run, store input references, assignments, and verification,
   then finalize it as `verified` or `rejected`.
5. Preferences may be revised while the round remains frozen. The roster cannot.
6. Close a round when appropriate; pending building runs must be finalized first.

Frozen refers to the ROSTER, not to an inability to revise preferences.
These are implementation defaults for review, not previously supplied user rules.
To keep this phase contained, roster changes after freezing and promotions
use a subsequent round. Automatic time-based promotion is not implemented.

Users can be deactivated without deleting historical records. Deactivation
prevents joining new rounds; it does not remove someone from an existing
frozen roster or invalidate that round automatically. Such operational
reassignment/withdrawal policies can be added later.

Ratings are append-only and use a provisional integer 1–5 scale. The API will
need to restrict writing to the authenticated assigned partner and reading to
administrators. Editing/withdrawing ratings is not implemented yet.

## Preference history

A draft version contains editable entries (delete/reinsert entries to reorder).
Only its newest draft can be submitted. Submission requires every opposite-side
participant exactly once, ranked from 1 to that side's size, with no ties.
After submission, both version metadata and entries are immutable.
A new version after a previous submission requires a nonblank explanation.
The explanation is supplied by the participant, not generated by the system.

A run references the exact submitted versions it used. Later revisions do not
rewrite them. `verified` means stable for the SNAPSHOT, not necessarily for
today's latest rankings. If `inputs_are_current` becomes 0, recheck existing
assignments against current preferences using the C++ verifier before declaring
current stability. A changed ranking is not proof of instability.

## Database vs application responsibilities

| Database enforces | C++ API/application must enforce |
| --- | --- |
| Foreign keys, roles of pair endpoints, unique ranks and targets. | Authenticate the caller; bind their identity to every request. |
| Complete rankings at submission. | Allow participants to edit only their own preferences. |
| Complete 1:1 assignments and a stored Stable result before marking verified. | Actually run the trusted matcher and verifier; SQL cannot establish mathematical stability. |
| Run requester references an active admin record. | Prevent impersonating that administrator by supplying their ID. |
| Ratings refer to the two assigned partners. | Admin-only rating reads; partner-only rating submissions. |
| Historical records cannot be casually updated/deleted. | Keep database file inaccessible to frontend clients; protect backups. |

There are no passwords or login sessions in this schema. SQLite has no
application-user account system for enforcing the intended HTTP permissions.
Do not expose raw SQL or the database file to the browser.
A malicious direct database writer can fabricate evidence or disable guards;
these constraints are integrity checks, not a substitute for authentication.

## Connections and transactions

Set these options on EVERY application connection, before a transaction:

```sql
PRAGMA foreign_keys = ON;
PRAGMA recursive_triggers = ON;
PRAGMA busy_timeout = 5000;
```

Foreign-key enforcement is connection-specific. Recursive triggers ensure
SQLite's replacement deletes also encounter history-protection triggers.
Use parameter binding (`sqlite3_prepare_v2`, bind values, step, finalize) in
C++ rather than constructing SQL from user strings. Avoid `INSERT OR REPLACE`
for application history. SQLite allows one writer at a time; no network
filesystem database sharing is part of this design.

For the first integrated matching endpoint, use one `BEGIN IMMEDIATE`
transaction to select latest submitted revisions, create the run/input
references, call C++ matching/verification, save results, finalize, and commit.
On any failure, roll back. Keep this transaction short; move to a version-check
workflow if future workloads make computation under the write lock too costly.

Database IDs are permanent; algorithm indices are local. Load participants
in a deterministic order, construct user-ID-to-index maps separately for both
sides, and translate stored target IDs to indices. Convert result indices
back to user IDs when saving. SQL ranks are 1-based; C++ vector positions
are 0-based. Reading entries ordered by rank builds the correct vectors.

## Migration policy

`migrations/001_initial.sql` applies ONCE to a new database and records
`PRAGMA user_version = 1`. It runs inside a transaction; it deliberately does
not hide an existing schema behind `IF NOT EXISTS`. Later changes should be
new numbered migrations, not reapplication of 001 to an existing database.
Back up persistent application data before future migration work.

## Useful SQL to inspect data

```sql
SELECT id, name, state FROM matching_rounds;
SELECT run_id, inputs_are_current FROM run_freshness;
SELECT mentor_id, mentee_id FROM assignments WHERE run_id = 1;
SELECT v.owner_id, v.revision, e.target_id, e.rank
FROM run_preferences rp
JOIN preference_versions v ON v.id = rp.version_id
JOIN preference_entries e ON e.version_id = v.id
WHERE rp.run_id = 1
ORDER BY v.owner_id, e.rank;
```

## Review questions — collected at the end

1. Why does a role belong to a round rather than permanently to a user?
2. Why do assignment rows belong to a run?
3. What do primary keys, foreign keys, UNIQUE, and CHECK enforce here?
4. How do uniqueness plus submission checks ensure a complete strict ranking?
5. Why preserve submitted preference versions instead of editing them in place?
6. What is the difference between historical verification and current-input freshness?
7. Why is a stored Stable label insufficient without actually calling the verifier?
8. What must roll back if only part of a matching run was saved?
9. Why cannot an is_admin column alone authenticate an HTTP caller?
10. How are permanent user IDs mapped to zero-based C++ indices?
